# 業務解釋力

原本要讀 `getReservationOverview` 的 SQL 才知道這些數字是什麼。Shadow 說明現在直接標出下列幾件事。

## 已經能說清楚的

- `totalReservations` 數的是預約列，不是學生人數。
- `attendanceRate` 的分子是 `已簽到` 列，分母是同一批預約列，含未簽到與已登記違規。
- 活動營運這三個已映射指標用的時間欄位是 `events.date`，不是 `reservations.createdAt`。
- `114-2` 的程式區間是 2026-02-01 到 2026-07-31，而且尾日算進去。契約另記半開終點為 2026-08-01 台北時間零時，兩者是否在 MySQL 得到相同筆數尚未驗證。
- 這支 API 的母體是全中心行政可見範圍，不是老師手上的班級名單。名單參與率是另一組指標與另一種日期比較。
- `englishPassRate` 若出現在 JSON，它是報名表 `hasCEFRB2` 標記，用檔案學期，不是活動出席率，也不是學習歷程達標率。
- 上述數字仍不可當作正式發布成果，也不可用來做因果結論。

## 仍然看不清楚或尚未驗證的

- `violationRate` 沒有 Metric ID。頁面有顯示，契約拒絕替它配一個相近指標。
- `totalEventCapacity` 與 `capacityBreakdown` 沒有單獨對上指標。活動場次 `ops.event.count` 不是這支回應的頂層欄位。
- 尾日 `2026-07-31` 的活動在 CAST `BETWEEN` 與半開區間下的筆數差，要等 L3 的 V06。
- 字串日期若帶時間或空白，CAST 後是否仍落在區間內，合成測試沒有用正式資料證明。
- 取消預約若仍留在 `reservations`，目前會留在總預約數裡。資料表沒有取消狀態列舉，實際刪除或保留要看資料，不在這次驗證內。

因此，預約列、出席率與活動日這三個最容易被說錯的點，現在不必再靠讀 SQL。違規率、名額分項，以及 MySQL 邊界筆數，還沒有被這次試點解決。
