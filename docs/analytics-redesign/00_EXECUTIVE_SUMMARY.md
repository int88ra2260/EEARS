# 00 執行摘要

研究日期：2026-10-31。方法：唯讀靜態追溯（路由掛載、服務、模型、前端入口）。未查正式資料庫，未改既有程式。

## 問題

EEARS 的「成效」不是一套分析，而是多輪需求疊出來的多套邏輯。它們共用學生學號，但證據來源、時間意義、統計母體與可下的結論並不相同。現有選單（含 2026-10-31 剛將學習成效頁分成「上呈／找人／看資源／比較與資料」）反映的是開發順序與近期整理，不是一套已驗證的評估架構。

## 核心發現

| ID | 發現 | 信心 | 需資料庫驗證 |
|---|---|---|---|
| F-01 | 至少六套並存的分析邏輯：活動營運、培力班級／報名、學習有伴、學習歷程名冊 B2、KPI 成對達標、分析快照（GSE／LVA）。名稱相近，母體與算法不同。 | 高 | 否 |
| F-02 | 「學期」至少有四種意義：活動日期落在學期區間、名冊 `semesterId`、培力匯入字串 `semester`、快照版本（跨學期累積，學期篩選刻意不進快照條件）。 | 高 | 否 |
| F-03 | B2 KPI 的分母是該學期名冊，分子用該生**全部** `status=valid` 的 `EtExamAttempt`，不限該學期考試日（`kpiReportService.loadAttemptsForStudents`）。 | 高 | 建議抽樣確認考試日落在名冊學期之外的比例 |
| F-04 | 學習歷程 `getSemesterB2Report` 是名冊學生的**歷史最佳技能**、CEFR rank ≥ 4。與 KPI 的聽讀成對／說寫成對不是同一指標。總覽 API 仍會在有 `semester` 時呼叫前者（`learningAnalyticsOverviewService`）。 | 高 | 否 |
| F-05 | 培力成績匯入 `normalizeCefrLevel` 會去掉 `B1+`／`B2+` 的加號（`bestepImportService.js`）。簡報級距與快照 CEFR 都無法還原加號。 | 高 | 需對原始檔與資料庫列比對，確認已匯入列是否已丟加號 |
| F-06 | `resource_effect_estimates.causal_effect` 與 `causal_claim_allowed` 存在於資料模型。前端技能成長把校正後 GSE 標成比較用，不是因果。名稱仍可能被讀成已證實的方案效果。 | 中 | 需查表是否有 `causal_claim_allowed=true` 的列 |
| F-07 | `routes/englishTestsRouter.js`、`routes/englishTestTrackingRouter.js` 存在於樹中，`server.js` 未掛載。不可當成線上分析。 | 高 | 否 |
| F-08 | 行為×成績的接合已散落：學習有伴 outcome、課／師／活動、技能成長、資源覆蓋、LVA。各自有前後測或參與窗，沒有全系統單一規則。 | 高 | 否 |
| F-09 | 權限會改變可見母體（班級範圍、學生範圍、中心總覽僅 admin／執行長），頁面不一定標示「你看到的不是全體」。 | 中 | 否（程式已見）；實際落差需用不同角色帳號看 |
| F-10 | 快照由學習歷程重建產生。匯入成績後，分析頁不會自動等於來源表，中間隔著投影與快照版本。 | 高 | 需對一次匯入批次核對「來源列 vs `lj_analytic_exams` vs 頁面」 |

## 建議方向（不是實作）

不要再把所有圖放進同一個「學習成效」殼。以三支時鐘分開：系統行為（這一季發生了什麼）、一次匯入測驗（這次考得怎樣）、名冊政策達標（這個學期要交的數字）。行為與成績的關聯另立，且必須寫明對齊規則。既有頁面先凍結語意，再決定保留、改名或改掛入口。詳見 `08_RECOMMENDED_BLUEPRINT.md`。
