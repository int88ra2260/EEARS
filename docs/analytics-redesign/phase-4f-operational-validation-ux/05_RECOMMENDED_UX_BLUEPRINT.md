採用「決策問題在上、既有營運明細在下」。不新增 API，不改權限，不改數字。以下是給之後實作的藍圖，這次沒有改 `AdminAnalyticsPage`。

## 誰在用

- 中心主任：看這個學期活動資源夠不夠、預約多不多、人有沒有到、哪種類型特別。
- 行政人員：沿用場次表與班級排行，處理個別活動與需要追蹤的班級。

兩種角色看到同一套全中心數字。權限沒有變成班級工作集。

## 第二屏

保留現有順序與欄位：

1. 依活動類型的名額、預約筆數、名額比。
2. 依場次的名稱、日期、類型、名額、預約筆數、名額比。
3. 依活動日的預約趨勢與簽到率趨勢。
4. 班級違規排行。

類型表上方寫明：這張表與頭條使用同一個活動日窗口；不要把類型列再加總後當成第二個總數。`items` 與 `byEventType` 是同一組數的兩種形狀，畫面只呈現其中一種表格。

場次日期若仍是原始字串，維持現在的顯示，不在前端自行改成另一種學期歸屬。

## 不放進核心區的資料

`englishPassRate` 繼續不要出現在第一屏。API 保留欄位。若以後要顯示，使用獨立補充區，標題見文案檔，並寫「報名表標記，與本頁預約無關」。沒有 L3 之前也不把它畫成趨勢。
