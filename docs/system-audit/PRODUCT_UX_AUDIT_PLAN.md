# Product UX Consistency Audit Plan

日期：2026-10-29。這是稽核計畫，不是稽核結果。本輪不改元件、樣式、文案或路由。

目標：用同一份檢查表看公開頁、學生頁、管理頁，找出使用者會感知到的不一致。領域不同而流程不同，不自動算缺陷。例如 CEFR 用在達標、GSE 用在比較，這是既定規則，稽核時標成「故意不同」。

證據分級沿用實作審查：已確認（程式看得到）、假設、需 runtime（必須開瀏覽器）。

---

## 範圍

路由清單不要手抄。稽核第一步用程式從 `reservation-frontend/src/App.js` 抽出全部 `<Route path>`，再分成三群。

| 群 | 怎麼認 | 已確認的例子 |
|----|--------|----------------|
| 公開 | 無 `RequireStudentAuth`、不在 `/admin` | `/`、`/events`、`/activities`、`/weekly`、`/practice/*`、`/announcements`、`/learning-resources`、`/regulations`、`/faq`、`/about`、`/privacy`、`/terms`、`/survey/:surveyId`、培力報名與組長流程 |
| 學生 | `/student/*`、`/account`、`/my-reservations`，以及雖屬學生資料但未套學生 JWT 的頁 | 登入、註冊、忘記密碼、進度、口說紀錄、課堂加分、我的預約。學習護照走 email OTP，不是學生 JWT。微學習可匿名，學號只在 sessionStorage |
| 管理 | `/admin` 底下，含 legacy redirect | 殼層、operations、學習分析、口說診斷、教師 dashboard、帳號重設。完整清單以 `App.js` 為準，權限以 `adminRouteAccess.js` 為準，選單以 `adminNavigation.js` 為準 |

不在這次 UX 稽核裡：後端 JSON 形狀、資料表正規化、權限鍵本身是否太多。那些已在 system audit。UX 只看使用者是否走得通、看得懂、失敗時知道下一步。

未掛上 `App.js` 的頁面（例如舊的 Learning Journey hub / student page）標成「原始碼在、路由不在」。不要把它們當正式畫面稽核，除非產品決定重新掛路由。

---

## 方法

1. 抽出路由表，註明 layout（公開 Header、學生、Admin shell）與守衛（無、學生 JWT、staff JWT、email OTP、公開 token）。
2. 每個畫面只做靜態閱讀：主要元件、表單、表格、空狀態元件、用語。
3. 每個群抽樣做瀏覽器檢查，不承諾 100 個路由都點過。抽樣必須含一條成功路徑、一條空資料、一條錯誤。
4. 問題寫成「觀察、影響、是否跨模組、建議修不修」。不在這份計畫裡直接改 UI。
5. 不把 Bootstrap 與自建 CSS 並存本身當成缺陷。只有使用者看得到的間距、層級或互動不一致才記錄。

建議抽樣，實作稽核時可增減：

- 公開：首頁、活動列表與一筆活動、一則公告、一個練習、問卷、培力報名。
- 學生：登入、我的預約、進度、口說紀錄、學習護照（對照它不是同一種登入）。
- 管理：登入後首屏、一個列表＋篩選、一個匯入、一個權限不足頁、一個 legacy redirect。

## 檢查維度

### 導覽與資訊架構

已確認的結構：

- 公開導覽在前台 Header。
- 管理選單是 `adminNavigation.js` 的分組，可見性另有測試。
- 進頁後是否擋人由 `getAdminRouteDeniedReason` 決定。選單看得到與路由進得去可能不一致。

稽核要對：

- 選單有、路由沒有。
- 路由有、選單沒有，而且不是故意的深連結。
- Legacy redirect 的舊網址是否還出現在可見選單。
- 學生個人功能是否都從同一組入口進入，或被拆到公開 Header 的不明顯位置。

需 runtime：實際點選、重新整理、直接貼 URL。

### Design tokens

靜態起點：`reservation-frontend/src/styles/design-system.css` 與重複出現的 `#2a5d9f`。

檢查：主色、危險色、間距、字級是否有第二套硬編碼；管理頁 inline style 是否讓同一層級的標題看起來不像同一個產品。記錄檔案即可，對比度要在瀏覽器量。

### 版面

看每頁是否遵守該群的殼：公開頁有沒有突然變成後台密度；後台列表有沒有各自發明頁首與返回。不要求所有頁同一欄數。

### 表單與表格

已確認：沒有共用的 `DataTable`。各模組自己畫表。

檢查：

- 必填、錯誤、送出中是否出現在欄位旁，或只靠整頁 alert。
- 篩選是否會留下可分享的 query，或只存在元件 state。
- 分頁、排序、空結果的位置是否同類型頁面差很多。
- 破壞性操作用 `ConfirmDialog` 還是 `window.confirm`。兩者並存是已確認的程式事實，視覺與鍵盤差異需 runtime。

### Loading、空、錯誤、成功

分類記錄，不要先改：

- 載入：全頁 spinner、區塊 spinner、沒有載入指示。
- 空：共用 empty 元件、一句話、空白。
- 錯誤：`ToastProvider`、頁內 alert、`console` 後無 UI。
- 成功：toast、停留原頁、導去別頁。

同一條流程裡，送出失敗若有的頁面有下一步、有的頁面只有英文 status text，記為跨模組問題。

### 無障礙

靜態：按鈕是否用 `div`、表單控制項有沒有 label、對話框有沒有標題、錯誤是否只靠顏色。

需 runtime：Tab 順序、焦點是否困在 modal、Esc 是否關閉、放大 200% 是否還能操作、`prefers-reduced-motion`。不要只看對比度截圖。

### 響應式

至少兩種寬度：360px 與 1280px。優先看活動日曆、後台寬表、報名多步驟。FullCalendar 在窄螢幕的實際行為是需 runtime，不能用「有 media query」代替。

### 雙語用語

對照同一概念在 Header、頁面、錯誤、信件預覽是否用同一個中文。

已知要核對、但尚未逐頁點完的詞：

- 培力英檢 / 英檢 / BESTEP。
- 學習歷程 / Learning Journey。
- 預約 / 報名（活動預約與英檢報名不是同一件事，混用才是問題）。
- CEFR 與 GSE。語意不同則標成故意，不要求改成同一個詞。

英文 UI 若只是開發用語出現在學生錯誤訊息，記下來。不要求這次把所有頁面做成雙語。

### 跨模組流程

用使用者任務串起來，而不是按資料夾。

| 任務 | 要看的斷點 | 已確認的程式差異 |
|------|------------|------------------|
| 預約一場活動 | 列表 → 問卷 gate → 登入 → 成功 / 黑名單 / 截止 | Gate 會 409 並給 `redirectUrl`。前端是否真的帶得回去，需 runtime |
| 取消自己的預約 | 我的預約 → 驗證 | 學生登入與取消驗證碼的關係以業務規則為準，UX 只看提示是否說得清 |
| 填問卷 | 公開問卷與預約被擋之後的問卷 | `/check` 只支持特定 id。其他問卷走別的 API 時，空狀態與錯誤可能不同 |
| 培力報名 | 公開表單、email、審核狀態 | 與學生帳號登入是不同入口 |
| 學習護照 | email OTP + captcha | 不是 `RequireStudentAuth` |
| 微學習 | 匿名可玩，學號為自願 | 與「我的紀錄」是否說明資料不會進正式歷程。需 runtime 看文案 |
| 後台匯入 | 選單上的 Import Center 與各模組自己的上傳 | Import Center 是導覽，不是統一上傳 API。UX 要看使用者會不會以為上傳一次就進所有模組 |

---

## 不列為不一致

- 公開頁可以不登入，學生個人資料必須登入。
- 學習護照用 email OTP，學習夥伴用公開 token，微學習可匿名。不要做成同一種登入畫面才算一致。
- Staff JWT 與學生 JWT 分開。
- 活動類型的 `cutoffHours`、`openRule` 不同，畫面文案應反映該活動，而不是寫死 2 小時或 7 天。
- CEFR 達標與 GSE 比較並存。

## 產出（未來執行時，不是本輪）

每個發現一行：路由、維度、觀察、已確認或需 runtime、嚴重度（擋任務 / 混淆 / 外觀）、是否跨模組。

結束條件：

- 路由表由 `App.js` 產生，三群都有覆蓋說明。
- 抽樣路徑有瀏覽器紀錄（成功、空、錯誤）。
- 用語表至少含上一節列出的詞。
- 沒有在稽核過程中改元件。

本輪限制：沒有開瀏覽器，所以這份文件沒有任何視覺缺陷結論。先前 system audit 提到的雙表格風格、`window.confirm` 與 toast 並存，只夠當檢查起點，不夠當 UX 結論。
